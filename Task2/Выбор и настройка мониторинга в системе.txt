Мотивация
 Зачем нужен мониторинг
  Система "Александрит" столкнулась с критическими проблемами, которые невозможно эффективно решить без полноценного мониторинга:

  1. Отсутствие видимости проблем: сейчас о проблемах компания узнает от клиентов, когда ущерб уже нанесен. Потеряны крупные контракты, растет недовольство клиентов B2C и B2B.
  2. Невозможность быстрой диагностики: без метрик специалистам требуется много времени на разбор проблем, что увеличивает время простоя и снижает эффективность команды.
  3. Отсутствие данных для масштабирования: нагрузка растет линейно (+100 заказов/месяц), но нет данных для обоснованного принятия решений о масштабировании инфраструктуры.
  4. Проблемы производительности: операторы жалуются на медленную загрузку MES, но нет объективных метрик для измерения и улучшения производительности.

 Что даст внедрение мониторинга
  Для бизнеса:
   - Снижение потерь от простоя: проактивное выявление проблем до их эскалации к клиентам
   - Улучшение SLA: возможность гарантировать клиентам конкретные сроки обработки заказов
   - Обоснование инвестиций: данные для принятия решений о найме или закупке серверов
   - Конкурентное преимущество: стабильная работа API привлечет больше B2B партнеров

  Для команды:
   - Быстрая диагностика: сокращение времени на поиск причин проблем с часов до минут
   - Превентивные действия: возможность решить проблему до того, как она повлияет на клиентов
   - Объективные метрики: данные для оптимизации производительности
   - Снижение нагрузки на поддержку: меньше инцидентов и быстрее их разрешение

Выбор подхода к мониторингу
 Для системы "Александрит" будем использовать комбинированный подход, применяя разные методологии для разных частей системы:
  1. RED-метрики для API и веб-приложений
   Применяется к: Shop API, CRM API, MES API, Internet Shop, CRM, MES
   Обоснование: эти компоненты обрабатывают запросы пользователей и API, поэтому критичны:

   Rate (Частота) - количество запросов в секунду
   Errors (Ошибки) - процент неуспешных запросов
   Duration (Длительность) - время обработки запросов

 2. USE-метрики для инфраструктуры
  Применяется к: Shop DB, MES DB, Messages Queue, 3D files storage, серверы приложений
  Обоснование: для инфраструктурных компонентов важно отслеживать использование ресурсов:

  Utilization (Утилизация) - процент использования ресурса
  Saturation (Насыщенность) - степень перегрузки ресурса
  Errors (Ошибки) - количество ошибок

 3. Бизнес-метрики для критичных процессов
  Применяется к: процесс обработки заказов
  Обоснование: нужно отслеживать метрики, напрямую связанные с бизнес-процессами:

  Время обработки заказа от создания до завершения
  Количество заказов в каждом статусе
  Время расчета стоимости 3D-модели

Метрики для отслеживания

 1. Shop API

  http_requests_total (counter)
   Зачем нужна: общее количество HTTP-запросов для понимания нагрузки на систему
   Ярлыки:
    method - HTTP метод (GET, POST, PUT, DELETE)
    endpoint - путь запроса (/api/orders, /api/products)
    status_code - код ответа (200, 400, 500)
    source - источник запроса (web, mobile, api)

  http_request_duration_seconds (histogram)
   Зачем нужна: измерение времени обработки запросов для выявления узких мест
   Ярлыки:
    method - HTTP метод
    endpoint - путь запроса
    status_code - код ответа

  file_upload_duration_seconds (histogram)
   Зачем нужна: отслеживание времени загрузки 3D-файлов - критично для пользовательского опыта
   Ярлыки:
    file_size_bucket - диапазон размера файла (small, medium, large)
    file_format - формат файла (stl, obj, fbx)

  file_upload_size_bytes (histogram)
   Зачем нужна: понимание распределения размеров загружаемых файлов для планирования хранилища
   Ярлыки:
    file_format - формат файла

 2. MES API

  price_calculation_duration_seconds (histogram)
   Зачем нужна: критичная метрика - расчет цены занимает 2-30 минут, нужно отслеживать и оптимизировать
   Ярлыки:
    model_complexity - сложность модели (low, medium, high) - на основе количества полигонов
    calculation_status - статус расчета (success, failure, timeout)

  price_calculation_polygon_count (histogram)
   Зачем нужна: корреляция времени расчета с количеством полигонов для прогнозирования
   Ярлыки:
    calculation_status - статус расчета

  orders_dashboard_load_time_seconds (histogram)
   Зачем нужна: операторы жалуются на медленную загрузку - нужно измерить и улучшить
   Ярлыки:
    filter_status - применяемый фильтр по статусам
    page_size - размер страницы пагинации

  http_requests_total (counter)
   Зачем нужна: количество запросов к MES API
   Ярлыки:
    method - HTTP метод
    endpoint - путь запроса
    status_code - код ответа
    user_role - роль пользователя (operator, admin)

  http_request_duration_seconds (histogram)
   Зачем нужна: время обработки запросов
   Ярлыки:
    method - HTTP метод
    endpoint - путь запроса

 3. CRM API

  http_requests_total (counter)
   Зачем нужна: количество запросов к CRM API
   Ярлыки:
    method - HTTP метод
    endpoint - путь запроса
    status_code - код ответа
    user_role - роль пользователя (seller, admin)

  http_request_duration_seconds (histogram)
   Зачем нужна: время обработки запросов
   Ярлыки:
    method - HTTP метод
    endpoint - путь запроса

 4. Messages Queue (RabbitMQ)

  rabbitmq_queue_messages (gauge)
   Зачем нужна: количество сообщений в очереди - рост может указывать на проблемы обработки
   Ярлыки:
    queue_name - имя очереди (order_created, status_changed, price_calculated)
    vhost - виртуальный хост

  rabbitmq_queue_messages_ready (gauge)
   Зачем нужна: количество необработанных сообщений - критично для выявления задержек
   Ярлыки:
    queue_name - имя очереди
    vhost - виртуальный хост

  rabbitmq_queue_consumers (gauge)
   Зачем нужна: количество активных консьюмеров - нужно для понимания, обрабатываются ли сообщения
   Ярлыки:
    queue_name - имя очереди
    vhost - виртуальный хост

  message_processing_duration_seconds (histogram)
   Зачем нужна: время обработки сообщений каждым сервисом
   Ярлыки:
    queue_name - имя очереди
    message_type - тип сообщения
    consumer_service - сервис-обработчик (shop_api, crm_api, mes_api)
    status - статус обработки (success, error, retry)

 5. Базы данных (Shop DB, MES DB)

  postgresql_connections_active (gauge)
   Зачем нужна: количество активных соединений для выявления утечек и планирования пула
   Ярлыки:
    database - имя базы данных
    state - состояние соединения (active, idle, idle_in_transaction)

  postgresql_connections_max (gauge)
   Зачем нужна: максимальное количество доступных соединений
   Ярлыки:
    database - имя базы данных

  postgresql_query_duration_seconds (histogram)
   Зачем нужна: время выполнения запросов для выявления медленных запросов
   Ярлыки:
    database - имя базы данных
    query_type - тип запроса (SELECT, INSERT, UPDATE, DELETE)

  postgresql_slow_queries_total (counter)
   Зачем нужна: количество медленных запросов (>1сек) - индикатор проблем с производительностью
   Ярлыки:
    database - имя базы данных
    table - таблица

  postgresql_database_size_bytes (gauge)
   Зачем нужна: размер базы данных для планирования хранилища
   Ярлыки:
    database - имя базы данных

 6. 3D files storage

  s3_object_count (gauge)
   Зачем нужна: количество файлов в хранилище
   Ярлыки:
    bucket - имя бакета

  s3_storage_size_bytes (gauge)
   Зачем нужна: общий размер хранилища для планирования емкости
   Ярлыки:
    bucket - имя бакета

  s3_operation_duration_seconds (histogram)
   Зачем нужна: время операций чтения/записи
   Ярлыки:
    operation - тип операции (get, put, delete)
    status - статус операции (success, error)

 7. Бизнес-метрики заказов

  orders_total (counter)
   Зачем нужна: общее количество созданных заказов для отслеживания роста бизнеса
   Ярлыки:
    source - источник заказа (web, api)
    status - текущий статус заказа

  orders_by_status (gauge)
   Зачем нужна: количество заказов в каждом статусе - для выявления узких мест и зависших заказов
   Ярлыки:
    status - статус заказа (INITIATED, FILE_UPLOADED, SUBMITTED, PRICE_CALCULATED, MANUFACTURING_APPROVED, MANUFACTURING_STARTED, MANUFACTURING_COMPLETED, PACKAGING, SHIPPED, CLOSED)

  order_processing_duration_seconds (histogram)
   Зачем нужна: время прохождения заказа через систему от создания до завершения
   Ярлыки:
    source - источник заказа (web, api)
    final_status - конечный статус (CLOSED, CANCELLED)

  order_status_transition_duration_seconds (histogram)
   Зачем нужна: время перехода между статусами для выявления задержек на конкретных этапах
   Ярлыки:
    from_status - начальный статус
    to_status - конечный статус

  order_sla_violations_total (counter)
   Зачем нужна: количество нарушений SLA (заказы дольше 3 недель) - критично для бизнеса
   Ярлыки:
    source - источник заказа
    violation_reason - причина нарушения (если известна)

  system_network_bytes_sent_total (counter)

   Ярлыки:
    instance - идентификатор инстанса

  system_network_bytes_received_total (counter)
   Зачем нужна: входящий сетевой трафик
   Ярлыки:
    instance - идентификатор инстанса
    interface - сетевой интерфейс

 9. Дополнительные метрики приложений

План действий

 Этап 1: Выбор и настройка инфраструктуры мониторинга (1-2 недели)

  1. Выбрать стек мониторинга

    Time-series база: Prometheus (open-source, де-факто стандарт для метрик)
    Визуализация: Grafana (open-source, богатые возможности)
    Алертинг: Alertmanager (интеграция с Prometheus)

  2. Развернуть инфраструктуру мониторинга

    Создать облачный инстанс для Prometheus (минимум 4GB RAM, 2 vCPU)
    Настроить Prometheus с retention 15 дней (минимум) для хранения метрик
    Развернуть Grafana на том же или отдельном инстансе
    Настроить Alertmanager для отправки уведомлений

  3. Настроить безопасность

    Ограничить доступ к Prometheus только с IP адресов компании
    Настроить аутентификацию в Grafana
    Создать роли: Admin (полный доступ), Developer (просмотр + редактирование дашбордов), Viewer (только просмотр)

Этап 2: Инструментирование приложений (2-3 недели)

  1. Shop API (SpringBoot)

     Подключить Micrometer + Prometheus registry
     Добавить кастомные метрики для загрузки файлов
     Настроить экспорт метрик на /actuator/prometheus

  2. CRM API (SpringBoot)

     Подключить Micrometer + Prometheus registry
     Настроить экспорт метрик на /actuator/prometheus

  3. MES API (C#)

     Подключить prometheus-net библиотеку
     Реализовать кастомные метрики для расчета цены и загрузки дашборда
     Настроить экспорт метрик на /metrics

  4. Frontend приложения (Internet Shop, CRM, MES)

     Рассмотреть использование RUM (Real User Monitoring) через встраивание JavaScript агента
     Альтернатива: серверная аналитика через Nginx access logs

  5. Бизнес-метрики заказов

     Реализовать инструментализацию в Shop API, CRM API и MES API
     Создать таблицу order_metrics_events для хранения событий переходов статусов
     Настроить периодический экспорт агрегированных метрик

Этап 3: Мониторинг инфраструктуры (1 неделя)

  1. Облачные системные метрики

     Установить Node Exporter на все EC2 инстансы
     Настроить Prometheus scraping для Node Exporter

  2. PostgreSQL

     Установить Postgres Exporter для Shop DB и MES DB
     Настроить подключение к базам с read-only правами
     Настроить Prometheus scraping для Postgres Exporter

  3. RabbitMQ

     Включить Prometheus plugin в RabbitMQ
     Настроить Prometheus scraping для RabbitMQ metrics endpoint

  4. S3 Storage

     Использовать CloudWatch Exporter для экспорта метрик S3 в Prometheus
     Альтернатива: разработать custom exporter для чтения метрик из S3 API

Этап 4: Создание дашбордов и алертов (1-2 недели)

  1. Создать дашборды в Grafana

     System Overview: общее состояние всех компонентов
     Shop API Dashboard: метрики Shop API с фокусом на загрузку файлов
     MES API Dashboard: метрики MES API с фокусом на расчет цены
     CRM API Dashboard: метрики CRM API
     Database Dashboard: метрики баз данных
     RabbitMQ Dashboard: состояние очередей
     Business Metrics Dashboard: бизнес-метрики заказов
     Infrastructure Dashboard: системные метрики всех инстансов

  2. Настроить алерты

     High error rate (>5% ошибок в течение 5 минут)
     Slow response time (p95 > 3 секунды в течение 10 минут)
     Price calculation timeout (>30 минут)
     RabbitMQ queue backlog (>1000 сообщений)
     Database connection pool saturation (>80%)
     System resource saturation (CPU >85%, Memory >90%, Disk >85%)
     Orders stuck in status (более 7 дней в одном статусе)
     SLA violations

  3. Настроить каналы уведомлений

     Интеграция с корпоративным email
     Интеграция с Slack/Telegram для критичных алертов
     On-call rotation для ночных инцидентов

Этап 5: Документация и обучение (1 неделя)

  1. Создать документацию

     Runbook для реагирования на алерты
     Инструкция по созданию новых дашбордов
     Инструкция по добавлению новых метрик в приложения

  2. Обучить команду

     Провести воркшоп для разработчиков по работе с метриками
     Провести сессию для бизнеса по интерпретации бизнес-метрик
     Провести тренинг для поддержки по реагированию на алерты

Дополнительное задание: Показатели насыщенности

 Пороговые значения насыщенности

  1. CPU Utilization
   Пороговое значение: 85%
   Обоснование: при утилизации CPU выше 85% система начинает испытывать задержки в обработке запросов. Оставляем 15% запас для пиковых нагрузок.
   Действия при превышении:
    - Warning (85-90%): создать тикет для анализа нагрузки и планирования вертикального/горизонтального масштабирования
    - Critical (>90%): автоматическое уведомление дежурной команды, ручное добавление инстанса или временное ограничение нагрузки

  2. Memory Utilization
   Пороговое значение: 90%
   Обоснование: при утилизации памяти выше 90% возможен OOM killer или swap, что критично снижает производительность.
   Действия при превышении:
    - Warning (90-95%): создать тикет для анализа потребления памяти и оптимизации
    - Critical (>95%): немедленное уведомление, проверка на утечки памяти, рестарт сервиса с увеличенной памятью

  3. Database Connection Pool
   Пороговое значение: 80% от max_connections
   Обоснование: при исчерпании пула соединений приложения начнут получать ошибки подключения.
   Действия при превышении:
    - Warning (80-90%): создать тикет для анализа использования соединений и увеличения пула
    - Critical (>90%): уведомление дежурной команды, анализ long-running запросов, временное увеличение max_connections

  4. Disk Space
   Пороговое значение: 85%
   Обоснование: при заполнении диска приложения перестанут работать. Нужен запас для логов и временных файлов.
   Действия при превышении:
    - Warning (85-90%): создать тикет для очистки старых данных и увеличения диска
    - Critical (>90%): немедленная очистка старых логов, увеличение диска, уведомление команды

  5. RabbitMQ Queue Length
   Пороговое значение: 1000 сообщений
   Обоснование: накопление сообщений указывает на проблемы обработки. При 1000+ сообщений задержки становятся значительными.
   Действия при превышении:
    - Warning (1000-5000): создать тикет для анализа производительности консьюмеров
    - Critical (>5000): уведомление команды, масштабирование консьюмеров, анализ причин замедления

  6. API Response Time (p95)
   Пороговое значение: 3 секунды
   Обоснование: Время ответа >3 секунд негативно влияет на пользовательский опыт.
   Действия при превышении:
    - Warning (3-5 сек): создать тикет для анализа производительности
    - Critical (>5 сек): уведомление команды, проверка медленных запросов к БД, анализ кода

  7. Price Calculation Duration
   Пороговое значение: 20 минут
   Обоснование: Средняя длительность 2-3 минуты, максимальная 30 минут. Порог 20 минут - индикатор проблем.
   Действия при превышении:
    - Warning (20-25 минут): логирование для анализа сложности модели
    - Critical (>30 минут): прерывание расчета с уведомлением пользователя, тикет для оптимизации алгоритма

  8. Error Rate
   Пороговое значение: 5%
   Обоснование: Нормальный error rate < 1%. При 5%+ страдает значительная часть запросов.
   Действия при превышении:
    - Warning (5-10%): анализ типов ошибок, создание тикета
    - Critical (>10%): немедленное уведомление, rollback последнего деплоя если применимо, анализ логов

 Автоматизация реагирования

  Приоритет 1 (Автоматическое действие):

   - CPU >90%: Auto-scaling при наличии готовых инстансов
   - Disk >95%: Автоматическая очистка старых логов (>30 дней)

  Приоритет 2 (Автоматический тикет + уведомление):

   - Memory >95%
   - Database connections >90%
   - Queue >5000 messages
   - Error rate >10%

  Приоритет 3 (Тикет без уведомления):

   - CPU >85%
   - Disk >85%
   - Response time >3sec
   - Queue >1000 messages
