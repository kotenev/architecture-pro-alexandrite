I. Архитектурное решение по логированию

II. Анализ систем компании и C4 диаграмму контейнеров в контексте планирования логирования.

 1. Компоненты системы, требующие сбора логов

  На основе анализа C4-диаграммы контейнеров выделены следующие критичные компоненты:

   1.1. Высокоприоритетные компоненты (требуют немедленного внедрения):

    а) MES API (C#): расчет стоимости, назначение заказов операторам, управление статусами;
    б) CRM API (SpringBoot): управление заказами, подтверждение производства;
    в) Shop API (SpringBoot): прием заказов, загрузка 3D-моделей;
    г) Messages Queue (RabbitMQ): критическая точка потери сообщений;
    д) MES DB (PostgreSQL): информация о заказах и их статусах;
    е) CRM DB (PostgreSQL): данные о клиентах и заказах;
    ё) Shop DB (PostgreSQL): заказы с точки зрения клиента.

   1.2. Среднеприоритетные компоненты:

    а) MES Frontend (React): пользовательские действия операторов;
    б) CRM Frontend (Vue): действия менеджеров по продажам;
    в) Shop Frontend (Vue): действия клиентов (ошибки JS, взаимодействие).

   1.3. Вспомогательные компоненты:

    3D File Storage: операции с файлами, ошибки хранения.

 3. Использование других уровней логирования

  3.1 DEBUG (отладка, dev/staging окружения)

   Когда использовать:

    а) детальная трассировка выполнения бизнес-логики;
    б) отладка интеграций с внешними системами;
    в) детальные данные о запросах/ответах API;
    г) промежуточные вычисления в расчете стоимости.

  3.2 WARN (предупреждения)

   Когда использовать:

    а) превышение нормального времени обработки (например, расчет > 5 минут);
    б) повторные попытки отправки сообщения в очередь;
    в) приближение к лимитам (память, CPU, connections);
    г) использование deprecated API endpoints;
    д) необычные паттерны использования (подозрительная активность).

  3.3 ERROR (ошибки)

   Когда использовать:

    а) неудачные попытки обработки заказа;
    б) ошибки соединения с БД или RabbitMQ;
    в) исключения в бизнес-логике;
    г) ошибки валидации критичных данных;
    д) таймауты при обращении к внешним сервисам;
    е) потеря сообщений в очереди.

  3.4 FATAL (критические ошибки)

   Когда использовать:

    а) Полная недоступность критичного сервиса;
    б) Потеря соединения с основной БД без возможности восстановления;
    в) Критическая ошибка, требующая немедленной остановки сервиса;
    г) Обнаружение компрометации безопасности.

III. Мотивация

 Почему необходимо внедрить логирование
 --------------------------------------

 Компания "Александрит" сталкивается с критическими проблемами, которые напрямую влияют на бизнес:

  1. Потеря заказов и отсутствие прозрачности
    - Клиенты жалуются на просроченные заказы
    - Невозможно отследить, где именно "застрял" заказ
    - Разбор проблем занимает много времени

  2. Масштабирование бизнеса
    - Линейный рост нагрузки (+100 заказов/месяц)
    - Открытие API для внешних продавцов
    - Увеличение количества жалоб после внедрения API

  3. Технические проблемы
    - Заказы "зависают" в непонятном состоянии
    - Сообщения теряются в RabbitMQ
    - Медленная загрузка дашборда MES

  4. Отсутствие инструментов для диагностики
    - Разработчики не могут быстро локализовать проблему
    - Поддержка тратит много времени на сбор информации
    - Нет исторических данных для анализа

 Что даст компании внедрение логирования
 ---------------------------------------

  Бизнес-ценность:
   1. Снижение количества жалоб клиентов: быстрое выявление и решение проблем
   2. Сохранение крупных контрактов: повышение надежности для B2B клиентов
   3. Улучшение репутации: прозрачность и быстрое решение проблем
   4. Снижение операционных затрат: автоматизация диагностики

  Технические преимущества:
   1. Быстрая диагностика проблем: от часов до минут
   2. Проактивное обнаружение проблем: до того, как клиент пожалуется
   3. Исторические данные: анализ трендов и паттернов
   4. Основа для мониторинга: алерты на основе логов

 Технические и бизнес-метрики
 ----------------------------

  Технические метрики:

   | Метрика                     | Текущее состояние    | Целевое состояние      | Измерение                                      |
   |-----------------------------|----------------------|------------------------|------------------------------------------------|
   | MTTR (Mean Time To Resolve) | 2-4 часа             | < 30 минут             | Время от обнаружения до решения проблемы       |
   | MTTD (Mean Time To Detect)  | 1-2 дня              | < 15 минут             | Время от возникновения проблемы до обнаружения |
   | Потери сообщений в очереди  | Неизвестно           | 0 необработанных > 1ч  | Мониторинг Dead Letter Queue                   |
   | Время диагностики заказа    | 20-30 минут          | < 2 минут              | Время поиска истории заказа                    |
   | Покрытие логированием       | ~20% (логи в stdout) | 95% критичных операций | Процент покрытых бизнес-операций               |

  Бизнес-метрики:

   | Метрика                   | Текущее состояние   | Целевое состояние  | Влияние на бизнес             |
   |---------------------------|---------------------|--------------------|-------------------------------|
   | Количество жалоб клиентов | Растет (+30%/месяц) | Снижение на 60%    | Удержание клиентов, репутация |
   | NPS (Net Promoter Score)  | Снижается           | Рост на 20 пунктов | Лояльность клиентов           |
   | Потерянные контракты B2B  | 3-5/квартал         | 0-1/квартал        | Прямая выручка                |
   | Время ответа поддержки    | 24-48 часов         | < 4 часов          | Удовлетворенность клиентов    |

 Приоритизация внедрения логирования и трейсинга
 -----------------------------------------------

  1. Первый этап (критичные системы)

   Системы для немедленного внедрения:

    а) RabbitMQ Integration Layer
       - почему: основная точка потери данных;
       - что логировать: все отправленные/полученные сообщения, ошибки доставки;
       - трейсинг: полная цепочка прохождения сообщения;
       - ожидаемый эффект: выявление 90% случаев потери заказов.

    б) MES API
       - почему: узкое место системы, долгие расчеты, назначение заказов;
       - что логировать: расчеты стоимости, смена статусов, назначения;
       - трейсинг: от получения заказа до завершения производства;
       - ожидаемый эффект: понимание причин задержек, оптимизация расчетов.

    в) CRM API
       - почему: точка подтверждения заказов, интеграция с MES;
       - что логировать: подтверждения, изменения статусов, закрытие заказов;
       - трейсинг: полный жизненный цикл заказа с точки зрения бизнеса;
       - ожидаемый эффект: прозрачность для менеджеров, быстрый разбор жалоб.

    Обоснование приоритета:
     - эти три компонента образуют критический путь обработки заказа;
     - 80% проблем связаны с потерей/зависанием заказов в этих системах;
     - быстрый ROI - результаты видны через 2-4 недели.

  2. Второй этап

   а) Shop API
      - почему: точка входа заказов B2C и B2B;
      - что логировать: создание заказов, загрузка моделей, отправка на расчет;
      - ожидаемый эффект: понимание пути клиента, оптимизация UX.

   б) Базы данных (MES DB, CRM DB, Shop DB)
      - почему: критичные операции изменения состояния;
      - что логировать: транзакции изменения статусов, создание заказов;
      - ожидаемый эффект: отслеживание несогласованности данных.

  3. Третий этап

   а) Frontend Applications
     - почему: понимание поведения пользователей, ошибки JS;
     - что логировать: ошибки, критичные действия пользователей;
     - ожидаемый эффект: улучшение UX, снижение количества ошибок.

  Почему не одновременно?

   - ограничены ресурсы команды (2 Java, 1 C#, 1 QA, 1 DevOps);
   - нужен итеративный подход с быстрой обратной связью;
   - сложность настройки и обучения команды;
   - необходимость доработки инфраструктуры (ELK/OpenSearch кластер).

 Политика безопасности
 ---------------------

  1. Доступ к логам:

   Доступ к OpenSearch Dashboards будет осуществляться по ролевой модели.

  2. Чувствительные данные:

   Личные данные пользователей (ФИО, адреса, телефоны) не должны попадать в логи.
   Для этого будет настроено маскирование данных на уровне сборщиков логов.

 Политика хранения
 -----------------

  1. Индексы: Будет создан отдельный индекс для каждого приложения (shop-api, crm-api, mes-api).

  2. Срок хранения:
   а) горячее хранилище (hot): 7 дней (для оперативного анализа).
   б) теплое хранилище (warm): 30 дней.
   в) холодное хранилище (cold): 90 дней (архивация в S3).

V. Необходимые мероприятия для превращения системы сбора логов в систему анализа логов.

 Алертинг
 --------

  Будут настроены алерты на следующие события:

   а) Рост числа ошибок: увеличение количества логов с уровнем ERROR на 20% в течение 10 минут.
   б) Задержки в обработке заказов: если заказ находится в одном статусе более 3-х дней.
   в) Недоступность сервиса: отсутствие логов от какого-либо сервиса в течение 15 минут.

 Поиск аномалий
 --------------

  Для выявления аномалий, таких как DDoS-атаки, будет использоваться модуль Anomaly Detection в OpenSearch.
  Он позволяет на основе исторических данных выявлять нетипичное поведение системы, например, резкий рост количества заказов.

 Обоснование выбора: OpenSearch
 ------------------------------

  Почему OpenSearch:

   а) лицензирование:

    - Apache 2.0 - полностью открытая лицензия;
    - нет рисков изменения лицензии (как случилось с Elasticsearch);
    - нет hidden costs или ограничений функциональности.

   б) производительность:

    - 100% совместимость с Elasticsearch API;
    - такая же производительность индексации и поиска;
    - горизонтальное масштабирование без ограничений.

   в) функциональность:

    - все функции ELK Stack (поиск, визуализация, алертинг);
    - встроенный Anomaly Detection (ML);
    - integration с Jaeger для трейсинга;
    - OpenSearch Dashboards аналогичен Kibana.

   г) экосистема:

    - гарантия развития (пожертвования от крупных облачных провайдеров);
    - большое сообщество (миграция из Elasticsearch);
    - немного меньше плагинов, чем у ELK (но основные есть).

   д) безопасность:

    - встроенный Security plugin (RBAC, audit logs);
    - шифрование at-rest и in-transit.

  Плюсы OpenSearch:

   а) стоимость: безоплатно (self-hosted) или доступные цены managed service;
   б) нет vendor lock: полная свобода миграции в будущем;
   в) совместимость: лёгкая миграция с ELK если уже используется;
   г) production-ready: используется в крупных облачных провайдерах и организациях;
   д) поддерживается в Yandex Cloud: доступна услуга Managed OpenSearch.

  Минусы OpenSearch:

   а) немного моложе: меньше истории, чем Elasticsearch
   б) меньше плагинов: но критичные есть, и экосистема растёт
   в) требует DevOps навыков: для self-hosted setup

  Чем не понравились другие продукты:

   а) ELK Stack:

    - Elastic License - риски ограничений в будущем
    - дороже при масштабировании
    - Elastic может изменить условия лицензирования снова

   б) Splunk:

    - очень дорого ($50K+/год для 1TB);
    - Команда не знакома с Splunk;
    - vendor lock-in - сложная миграция;
    - Splunk нельзя купить официально в РФ.

   в) Grafana Loki:

    - хорош для Kubernetes, но менее зрелый;
    - ограниченный полнотекстовый поиск;
    - нет встроенного ML/anomaly detection;
    - лучше подходит для метрик, чем для логов.

   г) Graylog:

    - SSPL лицензия (Server Side Public License): ограничения;
    - меньше функциональности для ML;
    - меньше community и экосистемы.
