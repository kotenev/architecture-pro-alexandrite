II. Анализ систем компании и C4 диаграмму контейнеров в контексте планирования логирования.

 1. Компоненты системы, требующие сбора логов

  На основе анализа C4-диаграммы контейнеров выделены следующие критичные компоненты:

   1.1. Высокоприоритетные компоненты (требуют немедленного внедрения):

    а) MES API (C#): расчет стоимости, назначение заказов операторам, управление статусами;
    б) CRM API (SpringBoot): управление заказами, подтверждение производства;
    в) Shop API (SpringBoot): прием заказов, загрузка 3D-моделей;
    г) Messages Queue (RabbitMQ): критическая точка потери сообщений;
    д) MES DB (PostgreSQL): информация о заказах и их статусах;
    е) CRM DB (PostgreSQL): данные о клиентах и заказах;
    ё) Shop DB (PostgreSQL): заказы с точки зрения клиента.

   1.2. Среднеприоритетные компоненты:

    а) MES Frontend (React): пользовательские действия операторов;
    б) CRM Frontend (Vue): действия менеджеров по продажам;
    в) Shop Frontend (Vue): действия клиентов (ошибки JS, взаимодействие).

   1.3. Вспомогательные компоненты:

    3D File Storage: операции с файлами, ошибки хранения.

 3. Использование других уровней логирования

  3.1 DEBUG (отладка, dev/staging окружения)

   Когда использовать:

    а) детальная трассировка выполнения бизнес-логики;
    б) отладка интеграций с внешними системами;
    в) детальные данные о запросах/ответах API;
    г) промежуточные вычисления в расчете стоимости.

  3.2 WARN (предупреждения)

   Когда использовать:

    а) превышение нормального времени обработки (например, расчет > 5 минут);
    б) повторные попытки отправки сообщения в очередь;
    в) приближение к лимитам (память, CPU, connections);
    г) использование deprecated API endpoints;
    д) необычные паттерны использования (подозрительная активность).

  3.3 ERROR (ошибки)

   Когда использовать:

    а) неудачные попытки обработки заказа;
    б) ошибки соединения с БД или RabbitMQ;
    в) исключения в бизнес-логике;
    г) ошибки валидации критичных данных;
    д) таймауты при обращении к внешним сервисам;
    е) потеря сообщений в очереди.

  3.4 FATAL (критические ошибки)

   Когда использовать:

    а) Полная недоступность критичного сервиса;
    б) Потеря соединения с основной БД без возможности восстановления;
    в) Критическая ошибка, требующая немедленной остановки сервиса;
    г) Обнаружение компрометации безопасности.

III. Мотивация

 Почему необходимо внедрить логирование
 --------------------------------------

 Компания "Александрит" сталкивается с критическими проблемами, которые напрямую влияют на бизнес:

  1. Потеря заказов и отсутствие прозрачности
    - Клиенты жалуются на просроченные заказы
    - Невозможно отследить, где именно "застрял" заказ
    - Разбор проблем занимает много времени

  2. Масштабирование бизнеса
    - Линейный рост нагрузки (+100 заказов/месяц)
    - Открытие API для внешних продавцов
    - Увеличение количества жалоб после внедрения API

  3. Технические проблемы
    - Заказы "зависают" в непонятном состоянии
    - Сообщения теряются в RabbitMQ
    - Медленная загрузка дашборда MES

  4. Отсутствие инструментов для диагностики
    - Разработчики не могут быстро локализовать проблему
    - Поддержка тратит много времени на сбор информации
    - Нет исторических данных для анализа

 Что даст компании внедрение логирования
 ---------------------------------------

  Бизнес-ценность:
   1. Снижение количества жалоб клиентов: быстрое выявление и решение проблем
   2. Сохранение крупных контрактов: повышение надежности для B2B клиентов
   3. Улучшение репутации: прозрачность и быстрое решение проблем
   4. Снижение операционных затрат: автоматизация диагностики

  Технические преимущества:
   1. Быстрая диагностика проблем: от часов до минут
   2. Проактивное обнаружение проблем: до того, как клиент пожалуется
   3. Исторические данные: анализ трендов и паттернов
   4. Основа для мониторинга: алерты на основе логов
