II. Системы для покрытия трейсингом

 Критические точки отказа в системе
 ----------------------------------
 После анализа архитектуры компании "Александрит" выявлены следующие критические места, где заказ может "сломаться" или зависнуть:

  1. Онлайн-магазин -> Shop API -> Messages Queue

   а) Потеря заказа при создании
   б) Ошибки при загрузке 3D-файлов
   в) Сбои при отправке сообщений в очередь

  2. Messages Queue -> MES API

   а) Потеря сообщений в очереди
   б) Долгий расчет стоимости (2-30 минут)
   в) Таймауты при загрузке файлов из S3 storage

  3. MES API -> Messages Queue -> CRM API

   а) Потеря результатов расчета
   б) Рассинхронизация статусов
   в) Дублирование сообщений

  4. CRM API -> Messages Queue -> MES API

   а) Потеря подтверждений заказа
   б) Несвоевременное получение заказа операторами

  5. Обновления статусов внутри MES

   а) Потеря информации о смене статусов
   б) Зависание в промежуточных статусах

 Список данных, которые должны попадать в трейсинг.
 --------------------------------------------------
 1. Обязательные данные в каждом спане:

  а) trace_id - уникальный идентификатор трейса (сквозной для всех операций заказа)
  б) span_id - идентификатор конкретной операции
  в) parent_span_id - идентификатор родительской операции
  г) order_id - идентификатор заказа
  д) timestamp - время начала операц
  е) duration - длительность операции
  ё) service_name - название сервиса
  ж) operation_name - название операции
  з) status - статус выполнения (success/error)

 2. Специфичные данные по операциям:

  - для Shop API:

   а) user_id
   б) file_id (для 3D-моделей)
   в) order_status
   г) file_size
   д) polygon_count

  - для Messages Queue:

   а) message_id
   б) queue_name
   в) routing_key
   г) exchange_name
   д) delivery_attempt
   е) edelivery_count

  - для MES API:

   а) operator_id
   б) calculation_duration
   в) price_calculated
   г) manufacturing_complexity
   д) file_processing_time

  - для CRM API:

   а) seller_id
   б) approval_time
   в) rejection_reason (если отклонен)

  - для S3 Storage:

   а) file_url
   б) upload_duration
   в) file_validation_status

III. Мотивация

 Почему нужен трейсинг
 ---------------------
 Компания "Александрит" столкнулась с критическими проблемами:

  1. Потеря заказов - клиенты жалуются на не полученные заказы, над которыми работали несколько месяцев.
  2. Непрозрачность процессов - невозможно отследить текущее состояние заказа в распределенной системе.
  3. Рост нагрузки - +100 заказов в месяц, открытие API для B2B-клиентов.
  4. Потеря контрактов - из-за проблем с заказами компания теряет крупных клиентов.
  5. Долгое расследование инцидентов - разработчики тратят много времени на поиск причин проблем.

 Трейсинг позволит:

  а) визуализировать путь заказа через все системы в реальном времени;
  б) быстро находить узкие места и точки отказа;
  в) сократить время расследования инцидентов с нескольких дней до минут;
  г) предотвратить потерю заказов через проактивный мониторинг;
  д) улучшить клиентский опыт за счет прозрачности процесса.

 Технические метрики
 ___________________

  1. MTTR (Mean Time To Resolution): снижение времени восстановления с 3 дней до 3 часов.
  2. Процент потерянных заказов: снижение с текущих 5% до меньше чем 1%.
  3. Время обнаружения инцидентов: с нескольких часов/дней до 5 минут.
  4. SLA выполнения заказов: повышение с текущих 70% до 95% и выше.
  5. Процент успешной доставки сообщений: мониторинг и достижение 99.5%.

 Бизнес-метрики
 --------------

  1. Customer Satisfaction (CSAT): рост с текущих низких показателей до >4.5/5
  2. Удержание клиентов: снижение оттока B2B-клиентов с текущих потерь к нулю
  3. Скорость обработки жалоб: снижение с нескольких дней до <1 часа
  4. Стоимость поддержки: снижение на 40% за счет автоматизации диагностики
  5. Конверсия новых B2B-клиентов: рост за счет демонстрации надежности системы
