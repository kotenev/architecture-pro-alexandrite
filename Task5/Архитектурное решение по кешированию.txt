III. Мотивация

 Проблемы, требующие решения
  1. Система MES испытывает критические проблемы производительности:

Медленная загрузка дашборда операторов - первая страница MES с фильтруемым списком заказов долго прогружается, несмотря на внедренные пагинацию и фильтры
Рост нагрузки - линейное увеличение на 100 заказов ежемесячно создает постоянно растущую нагрузку на БД
Конкуренция операторов - операторам критически важно видеть самые новые заказы первыми (влияет на их вознаграждение), что создает высокую частоту обращений к системе
Медленный расчет стоимости - операция расчета стоимости изделия занимает 2-3 минуты в среднем, до 30 минут для сложных моделей
Увеличение количества партнеров - после открытия API нагрузка выросла многократно

Внедрение кеширования в систему "Александрит" продиктовано острой необходимостью решения существующих проблем с производительностью, которые напрямую влияют как на внутренних пользователей, так и на клиентов компании.
Проблемы:
Низкая скорость работы операторов в MES: Операторы жалуются на медленную загрузку страниц в MES, в частности дашборда со списком заказов. Это напрямую влияет на их производительность и, как следствие, на скорость обработки заказов и вознаграждение.[1][2][3] Медленная загрузка, вероятно, связана с большим объемом данных, которые необходимо извлечь из базы данных и отобразить.[4][5][6][7]
Неудовлетворительная скорость выполнения заказов для новых клиентов: Новые клиенты, привлекаемые через API, сталкиваются с задержками в выполнении заказов. Это негативно сказывается на репутации компании и может привести к потере клиентов и крупных контрактов.
Рост нагрузки на базу данных: С ростом числа заказов и подключением новых продавцов через API нагрузка на базу данных MES (PostgreSQL) постоянно растет. Это усугубляет проблемы с производительностью и может привести к сбоям в работе системы.
Цели внедрения кеширования:
Ускорить загрузку дашборда в MES: Снизить время отклика при отображении списка заказов для операторов.
Повысить общую производительность MES-системы: Ускорить выполнение операций, связанных с чтением данных о заказах.
Снизить нагрузку на базу данных MES: Уменьшить количество запросов к основной базе данных за счет обслуживания части запросов из кеша.[8]
Элементы системы для кеширования:
В первую очередь, необходимо кешировать данные, которые часто запрашиваются, но редко изменяются. Наиболее очевидным кандидатом для кеширования является список заказов, отображаемый на дашборде в MES. Этот список постоянно запрашивается операторами, но данные в нем (особенно по старым заказам) меняются не так часто.

IV. Предлагаемое решение

 Тип кеширования: Серверное
  Обоснование выбора серверного кеширования:

   Централизованное управление - все инстансы приложений работают с единым источником кешированных данных
   Согласованность данных - при текущей архитектуре (один инстанс каждого приложения) клиентское кеширование создаст проблемы с синхронизацией
   Контроль инвалидации - серверное кеширование позволяет централизованно управлять актуальностью данных
   API для партнеров - клиентское кеширование не применимо для API-интеграций
   Масштабируемость - при будущем масштабировании инстансов приложений не потребуется изменять логику кеширования

 Почему НЕ клиентское кеширование:

  Невозможно контролировать обновление данных на клиентах
  Не применимо для API-интеграций
  Усложнит синхронизацию при конкурентном доступе операторов
  Не решит проблему нагрузки на БД со стороны API-запросов

 Выбор паттернов кеширования
 ---------------------------

  1. Для дашборда MES (список заказов): Cache-Aside

   Обоснование:
   ------------

   Преимущества Cache-Aside для этого сценария:

   Простота реализации и понимания
    Кеш не является критичным - при падении Redis приложение продолжит работу (читая из БД)
    Гибкость - можем кешировать только часто запрашиваемые данные
    Ленивая загрузка - кеш наполняется по мере необходимости

   Почему НЕ Write-Through:

    Избыточная сложность для read-heavy сценария
    Операторы преимущественно читают данные, редко изменяют
    Синхронная запись в кеш при каждом обновлении замедлит операции изменения статуса
    Большая часть обновлений приходит через RabbitMQ, что потребует дополнительной интеграции

   Почему НЕ Refresh-Ahead:

    Невозможно предсказать, какие именно фильтры и страницы будут запрошены следующими
    Избыточное потребление ресурсов на предварительную загрузку
    Сложность прогнозирования паттернов доступа операторов

  2. Для расчета стоимости: Cache-Aside с долгим TTL

   Обоснование:
   ------------

    Расчет стоимости для одинаковых 3D-моделей всегда дает одинаковый результат
    Кеширование по хешу файла модели предотвратит повторные дорогостоящие вычисления
    Cache-Aside идеален, так как мы кешируем только результаты уже выполненных расчетов

  3. Для API партнеров: Cache-Aside

   Обоснование:
   ------------

   API запросы могут иметь различные параметры фильтрации
   Нужна гибкость в управлении кешем
   Критично иметь fallback на БД при проблемах с кешем

VI. Стратегия инвалидации кэша.

Сравнительный анализ стратегий инвалидации:

    | Стратегия | Плюсы | Минусы | Применимость в данном случае |
    | :--- | :--- | :--- | :--- |
    | Программная (по событию) | Высокая актуальность данных, отсутствие лишних запросов к БД. | Требует более сложной логики в приложении. | **Подходит идеально.** Обеспечивает баланс между производительностью и актуальностью данных. |
    | **По времени (TTL)** | Простота реализации. | Возможна отдача неактуальных данных; при коротком TTL высокая частота обращений к БД. | Менее предпочтительна, так как сложно подобрать оптимальный TTL, который бы устроил бизнес. |
    | **По ключу** | Позволяет инвалидировать конкретные части кеша. | Усложняет логику работы с кешем. | Может быть рассмотрена как дополнение к программной инвалидации для более гранулярного контроля. |

VII. Дополнительное задание

 Рассмотрим два варианта реализации кеширования:

  | | Решение 1: Локальный кеш в MES API | Решение 2: Внешний распределенный кеш (Redis) |
  | :--- | :--- | :--- |
  | **Описание** | Использование in-memory кеша в рамках инстанса MES API. | Внедрение отдельного сервиса кеширования, например, Redis. |
  | **Диаграмма** | `MES API <-> In-memory Cache` | `MES API <-> Redis <-> MES DB` |
  | **Плюсы** | - Простота и быстрота внедрения. <br>- Отсутствие сетевых задержек при доступе к кешу. | - Масштабируемость: кеш может использоваться несколькими инстансами MES API. <br>- Устойчивость: кеш не зависит от жизненного цикла конкретного инстанса приложения. <br>- Поддержка различных структур данных. |
  | **Минусы** | - Немасштабируемость: при наличии нескольких инстансов MES API кеш будет несогласованным. <br>- Потеря кеша при перезапуске приложения. | - Усложнение архитектуры. <br>- Появление сетевых задержек. <br>- Необходимость в администрировании дополнительного сервиса. |

 Заключение
 __________

  На мой взгляд, **Решение 2 (Внешний распределенный кеш Redis)** является более предпочтительным, несмотря на некоторую сложность внедрения. Учитывая планы компании по освоению новых рынков сбыта и линейный рост нагрузки, масштабируемость является ключевым фактором. Использование локального кеша станет "бутылочным горлышком" при горизонтальном масштабировании MES API. Redis же обеспечит согласованность данных между всеми инстансами и станет надежным и производительным решением в долгосрочной перспективе.
