 Элементы системы для кеширования
 --------------------------------

  1. MES Dashboard (приоритет: критический)

   - список заказов с фильтрацией по статусам;
   - агрегированная статистика по статусам заказов.

  2. MES API для расчета стоимости (приоритет: высокий)

   - результаты расчета стоимости для 3D-моделей.

  3. MES API для внешних партнеров (приоритет: высокий)

   - информация о статусах заказов;
   - cписок заказов партнера.

III. Мотивация

   Внедрение кеширования в систему "Александрит" продиктовано острой необходимостью решения существующих проблем с производительностью,
 которые напрямую влияют как на внутренних пользователей, так и на клиентов компании.

 Проблемы:

  1) Низкая скорость работы операторов в MES: операторы жалуются на медленную загрузку страниц в MES, в частности дашборда со списком заказов.
  Это напрямую влияет на их производительность и, как следствие, на скорость обработки заказов и вознаграждение.
  Медленная загрузка, вероятно, связана с большим объемом данных, которые необходимо извлечь из базы данных и отобразить.

  2) Неудовлетворительная скорость выполнения заказов для новых клиентов: новые клиенты, привлекаемые через API, сталкиваются с задержками в выполнении заказов.
  Это негативно сказывается на репутации компании и может привести к потере клиентов и крупных контрактов.

  3) Рост нагрузки на базу данных: с ростом числа заказов и подключением новых продавцов через API нагрузка на базу данных MES (PostgreSQL) постоянно растет.
  Это усугубляет проблемы с производительностью и может привести к сбоям в работе системы.


 Цели внедрения кеширования:

  1) Ускорить загрузку дашборда в MES: Снизить время отклика при отображении списка заказов для операторов.
  2) Повысить общую производительность MES-системы: Ускорить выполнение операций, связанных с чтением данных о заказах.
  3) Снизить нагрузку на базу данных MES: Уменьшить количество запросов к основной базе данных за счет обслуживания части запросов из кеша.

Элементы системы для кеширования:

    В первую очередь, необходимо кешировать данные, которые часто запрашиваются, но редко изменяются.
  Наиболее очевидным кандидатом для кеширования является список заказов, отображаемый на дашборде в MES.
  Этот список постоянно запрашивается операторами, но данные в нем (особенно по старым заказам) меняются не так часто.

IV. Предлагаемое решение

 Тип кеширования: Серверное

  Обоснование выбора серверного кеширования:

   а) централизованное управление - все инстансы приложений работают с единым источником кешированных данных;
   б) согласованность данных - при текущей архитектуре (один инстанс каждого приложения) клиентское кеширование создаст проблемы с синхронизацией;
   в) контроль инвалидации - серверное кеширование позволяет централизованно управлять актуальностью данных;
   г) API для партнеров - клиентское кеширование не применимо для API-интеграций;
   д) масштабируемость - при будущем масштабировании инстансов приложений не потребуется изменять логику кеширования.

 Почему НЕ клиентское кеширование:

  - невозможно контролировать обновление данных на клиентах;
  - не применимо для API-интеграций;
  - усложнит синхронизацию при конкурентном доступе операторов;
  - не решит проблему нагрузки на БД со стороны API-запросов.

 Выбор паттернов кеширования
 ---------------------------

  1. Для дашборда MES (список заказов): Cache-Aside

   Обоснование:
   ------------

   Преимущества Cache-Aside для этого сценария:

    - простота реализации и понимания;
    - кеш не является критичным: при падении Redis приложение продолжит работу (читая из БД);
    - гибкость: можем кешировать только часто запрашиваемые данные;
    - ленивая загрузка: кеш наполняется по мере необходимости.

   Почему НЕ Write-Through:

    - избыточная сложность для read-heavy сценария;
    - операторы преимущественно читают данные, редко изменяют;
    - синхронная запись в кеш при каждом обновлении замедлит операции изменения статуса;
    - большая часть обновлений приходит через RabbitMQ, что потребует дополнительной интеграции.

   Почему НЕ Refresh-Ahead:

    - невозможно предсказать, какие именно фильтры и страницы будут запрошены следующими;
    - избыточное потребление ресурсов на предварительную загрузку;
    - сложность прогнозирования паттернов доступа операторов.

  2. Для расчета стоимости: Cache-Aside с долгим TTL

   Обоснование:
   ------------

    - расчет стоимости для одинаковых 3D-моделей всегда дает одинаковый результат;
    - кеширование по хешу файла модели предотвратит повторные дорогостоящие вычисления;
    - Cache-Aside идеален, так как мы кешируем только результаты уже выполненных расчетов.

  3. Для API партнеров: Cache-Aside

   Обоснование:
   ------------

   - API запросы могут иметь различные параметры фильтрации;
   - нужна гибкость в управлении кешем;
   - критично иметь fallback на БД при проблемах с кешем.

VI. Стратегия инвалидации кэша.

 Сравнительный анализ стратегий инвалидации:

  | Стратегия                | Плюсы                                                        | Минусы                                                                               | Применимость в данном случае                                                                    |
  | :----------------------- | :----------------------------------------------------------- | :----------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------- |
  | Программная (по событию) | Высокая актуальность данных, отсутствие лишних запросов к БД | Требует более сложной логики в приложении                                            | Подходит идеально. Обеспечивает баланс между производительностью и актуальностью данных         |
  | По времени (TTL)         | Простота реализации                                          | Возможна отдача неактуальных данных; при коротком TTL высокая частота обращений к БД | Менее предпочтительна, так как сложно подобрать оптимальный TTL, который бы устроил бизнес      |
  | По ключу                 | Позволяет инвалидировать конкретные части кеша               | Усложняет логику работы с кешем                                                      | Может быть рассмотрена как дополнение к программной инвалидации для более гранулярного контроля |

VII. Дополнительное задание

 Рассмотрим два варианта реализации кеширования:

  |           | Решение 1: Локальный кеш в MES API                                                                                             | Решение 2: Внешний распределенный кеш (Redis)                                                                                                                                                    |
  | :-------- | :----------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | Описание  | Использование in-memory кеша в рамках инстанса MES API                                                                         | Внедрение отдельного сервиса кеширования, например, Redis                                                                                                                                        |
  | Диаграмма | MES API <-> In-memory Cache                                                                                                    | MES API <-> Redis <-> MES DB                                                                                                                                                                     |
  | Плюсы     | Простота и быстрота внедрения; отсутствие сетевых задержек при доступе к кешу                                                  | Масштабируемость: кеш может использоваться несколькими инстансами MES API; устойчивость: кеш не зависит от жизненного цикла конкретного инстанса приложения; поддержка различных структур данных |
  | Минусы    | Немасштабируемость: при наличии нескольких инстансов MES API кеш будет несогласованным; потеря кеша при перезапуске приложения | Усложнение архитектуры; появление сетевых задержек; необходимость в администрировании дополнительного сервиса                                                                                    |

 Заключение
 __________

    Решение 2 (внешний распределенный кеш на Redis) является более предпочтительным, несмотря на некоторую сложность внедрения.
  Учитывая планы компании по освоению новых рынков сбыта и линейный рост нагрузки, масштабируемость является ключевым фактором.
  Использование локального кеша станет "бутылочным горлышком" при горизонтальном масштабировании MES API.
  Redis же обеспечит согласованность данных между всеми инстансами и станет надежным и производительным решением в долгосрочной перспективе.
